# Стратегия обновления связки server-client без потери данных

- Статус: план следующего отдельного патча
- Область: zero-config Docker bootstrap
- Не является готовой пользовательской функцией

## Цель

Будущая команда:

```bash
python bootstrap.py update
```

должна обновлять backend и frontend из подтверждённой версии проекта, не
удаляя PostgreSQL volume, автоматически созданные secrets и аккаунты.

## Главная граница

Данные и код уже живут в разных местах:

- PostgreSQL хранится в named Docker volume;
- secrets хранятся в отдельном закрытом volume;
- backend/frontend собираются в Docker images;
- контейнеры являются заменяемыми процессами.

Поэтому обновление не должно выполнять `git pull` внутри работающего
контейнера. Контейнер с исходниками, Git credentials и частично обновлённым
рабочим деревом сложнее проверить и откатить. Правильная единица обновления —
новый versioned image или новая проверенная сборка, а не изменение файлов
внутри старого контейнера.

## Предлагаемый поток

1. Получить update lock, чтобы два обновления не шли одновременно.
2. Проверить Docker, свободное место, текущую версию и состояние stack.
3. Сохранить вне Docker volume:
   - `pg_dump` пользовательской БД;
   - текущую версию приложения;
   - digest текущих images;
   - manifest обновления.
4. Получить код точного commit/tag либо pull versioned OCI images.
5. Собрать/проверить новую связку рядом со старой.
6. Проверить совместимость миграций и применить только forward migration.
7. Переключить Compose на новые images.
8. Дождаться health/readiness backend и web gateway.
9. Выполнить короткий authenticated smoke.
10. Зафиксировать update report.

PostgreSQL и secrets volumes на шагах 4–9 не пересоздаются.

## Rollback

Откат контейнеров возможен только если миграции новой версии совместимы со
старым кодом. Поэтому каждая миграция обновляемой линии должна следовать
правилу expand/contract:

1. сначала добавить новые nullable/default-compatible структуры;
2. выпустить код, который понимает старую и новую форму;
3. перенести данные;
4. удалять старую форму только в более позднем релизе.

Если readiness новой версии не проходит:

- остановить новые контейнеры;
- вернуть предыдущие image digests;
- запустить старую связку на том же volume;
- не восстанавливать dump автоматически, пока не доказано, что миграция
  изменила данные несовместимо.

Автоматическое восстановление dump является отдельным destructive действием и
должно требовать явного подтверждения.

## Источник обновления

Первая реализация может поддерживать только один доверенный источник:

- GitHub Release с version manifest и SHA-256;
- либо OCI registry с immutable tag/digest.

Обновление напрямую из плавающей `main` допустимо только как developer mode.
Для обычного пользователя лучше обновляться на конкретный tag/commit: иначе
одна кнопка в разное время получает разный код, а rollback становится
неопределённым.

## Что должен показывать клиент

Кнопка `Обновить связку server-client` не должна сама выполнять опасную часть в
браузере. Она может вызвать локальный bootstrap updater и показать:

- текущую и доступную версию;
- создан ли backup;
- этап build/pull/migration/restart/readiness;
- сохранились ли volumes;
- путь к update report;
- возможность вернуть предыдущую версию контейнеров.

## Обязательные проверки будущего патча

- stop/start сохраняет аккаунт и доски;
- повторный update идемпотентен;
- закрытый Docker даёт одну понятную ошибку до записи;
- ошибка build не трогает текущий stack;
- ошибка readiness возвращает старые images;
- secrets не попадают в report;
- update с чистой beta.3 на тестовую следующую версию проходит на Windows и
  Linux;
- backup JSON доски до и после обновления логически эквивалентны.
